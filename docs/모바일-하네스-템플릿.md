# CLAUDE.md — {{PROJECT_NAME}} 하네스 (모바일 앱)

> **이 파일은 모바일 앱 프로젝트용 재사용 하네스 템플릿이다.** 새 프로젝트 루트에 `CLAUDE.md`로 복사한 뒤 `{{…}}` 자리표시자를 채우고, 켜지 않은 선택 규칙은 지운다.
> 대상 스택: **백엔드 Kotlin + Spring Boot / 앱 TypeScript + React Native(Expo)**. iOS·Android를 한 코드로 만든다.
> 구성: **Part A 공통 필수**(모든 프로젝트) + **Part B 선택 규칙**(조건에 해당할 때만 켬). 처음 개발하는 팀은 **Part A만 지키고 시작**하고, 선택 규칙은 필요해질 때 켠다. 기본 범위는 **로컬 개발 + 시뮬레이터/에뮬레이터 검증**까지이고, 스토어 출시는 S10.
> 출처: 실무 백오피스 프로젝트(Kotlin·Spring Boot·React)에서 쓰던 설계 규율과 하네스 계층을 모바일 앱 환경에 맞게 일반화.
> 기술 스택 버전 기준일: **2026-09-29** (Maven Central · npm registry · Expo SDK 57 `bundledNativeModules.json` · Adoptium · endoflife.date 실측).

"하네스(harness)"란 AI 코딩 에이전트가 저장소의 규칙·절차·게이트 안에서만 일하도록 감싸는 틀이다. AI에게 자유를 다 주는 대신, **사람이 지키던 규칙을 파일로 코드화**하고 그 안에서 일하게 한다.

## 0. 적용 방법 (새 프로젝트에 붙일 때 1회)

1. 이 파일을 새 저장소 루트에 `CLAUDE.md`로 복사한다.
2. 자리표시자를 치환한다.
   | 자리표시자 | 예시 |
   |---|---|
   | `{{PROJECT_NAME}}` | `habit-tracker` |
   | `{{BASE_PACKAGE}}` | `com.example.habit` |
   | `{{BACKEND_DIR}}` / `{{MOBILE_DIR}}` | `backend` / `mobile` |
   | `{{APP_SCHEME}}` | `habittracker` (딥링크·소셜 로그인 리다이렉트용 URL 스킴, 영문 소문자) |
   | `{{BUNDLE_ID}}` | `com.example.habit` (iOS `bundleIdentifier` · Android `package`. 출시 후엔 바꿀 수 없다) |
   | `{{AI_SERVICE}}` | `ai-service` (S4를 켤 때만) |
3. **§9 선택 규칙을 고른다.** 각 규칙의 "켜는 조건"에 해당하지 않으면 그 규칙을 통째로 지운다. 켠 규칙은 §1 체크리스트에 표시한다. 애매하면 끄고 시작한다 — 나중에 켜는 건 쉽지만, 필요 없는 구조를 걷어내는 건 어렵다.
4. 코드가 생기면 §7 "명령어"를 **실제로 돌려 본** 명령으로 교체한다. 추정 명령을 남겨두지 않는다.
5. 규모가 커지면 §10대로 파일을 쪼갠다.
6. 버전 표(§2)는 프로젝트를 만드는 시점에 한 번 더 확인한다. 이 표는 기준일 스냅샷이다. 앱 쪽은 **Expo SDK 버전 하나만 정하면 나머지는 `npx expo install`이 맞춰 준다**(§5-8).

## 3. 전역 규칙 (백엔드·앱 공통)

어느 레이어에서 작업하든 지키는 경계. 하나라도 어기면 리뷰에서 반려한다.

1. **시크릿·설정을 코드에 하드코딩하지 않는다** — 백엔드는 `application.yml`·소스 코드에 비밀번호·API 키를 쓰지 않고 `${ENV}`로 주입한다. 로컬은 `.env`(반드시 `.gitignore`)에 둔다. ⚠ Spring Boot는 `.env`를 자동으로 읽지 않는다 — `application.yml`에 `spring.config.import: optional:file:.env[.properties]`를 넣어야 값이 들어간다(없으면 `${...}`를 못 풀어 부팅 실패). (배포 환경의 시크릿 관리는 S10, Vault는 S5) 기능을 지우면 그것을 먹이던 설정(env·프로퍼티 클래스·시크릿 키)까지 끝까지 따라가 지운다. **앱에는 시크릿을 아예 넣지 않는다**(§3.1-11).
2. **스키마 변경은 Flyway 마이그레이션으로만** — DB에 직접 DDL을 치지 않는다. 한 번 적용된 마이그레이션 파일은 수정하지 않고 새 파일을 추가한다.
3. **API 계약은 camelCase** — 응답의 `id`는 항상 포함·보존.
4. **API 경로는 `/api/v1/` 접두사** — 앱은 한번 설치되면 사용자가 업데이트할 때까지 **옛 버전이 계속 돌아간다.** 호환을 깨야 할 때 `/v2`를 따로 열 수 있도록 처음부터 버전을 붙인다. (내부·관리자 API를 나눠야 하면 S6)
5. **모든 코드 변경은 TDD** — 실패하는 테스트 → 최소 구현 → 리팩터. 테스트 없는 동작 변경은 완료로 인정하지 않는다. 절차·게이트는 §8 Layer 5.

### 3.1 보안·인증 (인터넷에 공개되는 서비스 기준)

> 서비스가 인터넷에 열리는 순간 **모든 요청은 공격자가 보낸 것일 수 있다**고 가정한다. 그리고 **앱 설치 파일은 누구나 풀어 볼 수 있다**고 가정한다. 아래는 처음 만드는 모바일 프로젝트에서 가장 자주 뚫리는 곳들이다.

**인증 — 로그인한 사람이 누구인가**

1. **로그인은 소셜 로그인(OAuth2/OIDC)부터 고려하고, 신원 확인은 서버가 한다** — 앱은 `expo-auth-session`(PKCE)으로 로그인한 뒤 받은 **ID 토큰을 서버로 보내고, 서버가 서명·발급자(`iss`)·대상(`aud`)·만료(`exp`)를 검증**(Google 등은 iOS·Android 클라이언트 ID가 따로라 `aud`가 플랫폼마다 다르다 — 허용 `aud`는 **클라이언트 ID 목록**을 환경변수로 두고 그 안에 있는지 확인)한 뒤 자체 토큰을 발급한다. 앱이 보낸 이메일·사용자 ID를 그대로 믿지 않는다. 비밀번호를 직접 받는다면 Spring Security `PasswordEncoder`(기본 bcrypt)로 해시만 저장한다. 평문 저장·직접 만든 암호화 금지.
2. **토큰은 기기 보안 저장소에** — 리프레시 토큰은 `expo-secure-store`(iOS Keychain / Android Keystore)에, 액세스 토큰은 메모리(스토어)에만 둔다(인증 스토어에 Zustand `persist`를 붙이지 않는다 — 붙이면 AsyncStorage에 평문으로 저장된다). **`AsyncStorage`·MMKV·일반 파일에는 토큰을 저장하지 않는다**(암호화되지 않아 기기·백업에서 그대로 읽힌다).
3. **액세스 토큰은 짧게, 리프레시 토큰은 서버가 통제** — 액세스 토큰은 짧은 만료(예: 15분). 리프레시 토큰은 서버 DB에 **해시로** 저장하고, 쓸 때마다 새 것으로 교체(rotation)하며, 로그아웃·탈퇴·기기 분실 시 서버에서 폐기한다. 이미 교체된 리프레시 토큰이 다시 오면 탈취로 보고 그 사용자의 토큰을 전부 폐기한다.
   ⚠ **앱의 토큰 갱신은 한 번에 하나만** — 화면 하나가 요청 여러 개를 동시에 보내 동시에 401을 받으면, 갱신이 여러 번 호출되고 두 번째부터 "재사용"으로 판정되어 **사용자가 무작위로 강제 로그아웃**된다. 인터셉터는 진행 중인 갱신 Promise를 공유하고, 기다리던 요청은 그 결과로 재시도한다.
4. **API는 무상태(stateless) 토큰 인증으로** — `SessionCreationPolicy.STATELESS`, 인증은 `Authorization: Bearer` 헤더로만. **쿠키로 인증하지 않는 API라서 CSRF 보호를 끄는 것은 허용**된다(CSRF는 브라우저가 쿠키를 자동으로 붙이는 것을 노리는 공격이다). 단, 나중에 웹 클라이언트나 쿠키 인증을 추가하면 웹 앱 템플릿의 CSRF 규칙대로 다시 켠다.
   **개발용 로그인은 `local` 프로필에만** — 소셜 로그인은 시뮬레이터·curl·Maestro에서 자동화하기 어렵다. `@Profile("local")`인 개발 전용 로그인 API(시드 계정으로 토큰 발급)를 두고, 다른 프로필에서는 빈 자체가 등록되지 않게 한다. 이 API가 운영에 켜지면 누구나 아무 계정으로 로그인하는 사고가 된다 — "local 외 프로필에서 404" 테스트로 보장한다.

**인가 — 이 사람이 이걸 해도 되는가** 5. **권한 검사는 서버에서** — 앱에서 버튼을 숨기는 건 보안이 아니다(API는 누구나 직접 호출할 수 있다). 모든 API에 `@PreAuthorize`(설정은 §4-7). 6. **본인 데이터인지 확인한다(IDOR 방지)** — `GET /orders/{id}`에서 로그인 사용자가 그 주문의 주인인지 서버가 확인한다. ID만 바꿔서 남의 데이터가 보이면 사고다.

**입력 — 들어오는 값은 전부 의심한다** 7. **서버에서 다시 검증한다** — 앱의 Zod 검증은 사용자 편의용이고, 진짜 검증은 서버 Bean Validation이다. 사용자가 입력한 HTML을 `WebView`로 그리지 않는다(스크립트 실행 위험). 8. **SQL은 파라미터 바인딩만** — JPA 메서드·`@Query`의 `:param`을 쓰고, 문자열을 이어 붙여 쿼리를 만들지 않는다(SQL 인젝션). 9. **파일·사진 업로드는 확장자·MIME·크기를 서버에서 제한**하고, 업로드한 파일을 실행 가능한 경로에 두지 않는다. 저장 파일명은 서버가 새로 만든다. **사진의 EXIF 위치 정보(GPS)는 저장 전에 제거**한다 — 사진 한 장으로 집 주소가 새는 흔한 사고다. 10. **딥링크로 들어온 값도 외부 입력이다** — `myapp://reset?token=...` 같은 링크의 파라미터는 검증하고, 로그인 토큰·비밀값을 URL에 담지 않는다.

**노출 — 밖으로 나가는 것을 통제한다** 11. **앱에 들어간 값은 전부 공개된 값이다** — `EXPO_PUBLIC_` 환경변수, `app.config`의 `extra`, 코드에 쓴 문자열은 설치 파일을 풀면 누구나 볼 수 있다. 결제·AI·지도 등 **비밀 키가 필요한 외부 API는 반드시 백엔드를 거쳐** 호출한다. 12. **보안 헤더를 끄지 않는다** — Spring Security 기본 헤더를 "에러가 나서" 끄지 않는다. (HTTPS는 S10) 13. **에러 응답에 내부 정보를 싣지 않는다** — 스택 트레이스·SQL·서버 경로를 응답에 넣지 않는다. 사용자에겐 일반 메시지, 상세는 서버 로그에. 14. **로그인·회원가입·비밀번호 재설정·인증번호 발송에 요청 횟수 제한(rate limit)** — 무차별 대입과 문자/메일 폭탄 방지. 서버에서 Bucket4j 같은 라이브러리로 IP·계정별 제한을 건다.

**개인정보** 15. **필요한 것만 수집하고, 권한도 필요한 것만 요청한다** — 쓰지 않을 개인정보·기기 권한(위치·연락처 등)은 처음부터 요청하지 않는다. 16. **로그에 개인정보·비밀값을 남기지 않는다** — 서버 로그와 앱의 `console.log` 모두. 비밀번호·토큰·전화번호 전체 등. 요청 바디를 통째로 로그에 찍지 않는다. 17. **탈퇴 시 개인정보는 실제로 지우거나 익명화한다** — §4-5의 소프트 삭제(`deleted_at`)는 "안 보이게"일 뿐 데이터는 남는다. 개인 식별 컬럼은 탈퇴 처리 때 삭제·익명화한다. 18. **로그아웃·탈퇴 시 기기에 남은 데이터를 지운다** — Secure Store의 토큰, TanStack Query 캐시, Zustand 스토어, 임시 파일. 다음 사람이 같은 기기로 로그인해도 이전 데이터가 보이면 안 된다. 19. **의존성 취약점 점검** — `npm audit`, 백엔드 의존성은 Boot BOM 최신 패치 유지.

## 4. 백엔드 필수 규칙

> 좋은 규칙은 추상 원칙이 아니라 **아팠던 경험의 응축**이다. 규칙을 추가할 땐 "왜 / 어떤 사고에서"를 함께 적는다(§11).

1. **계층을 나누고 의존은 한 방향으로** — `controller → service → repository`. Controller는 요청 검증·응답 변환만, 비즈니스 로직은 Service에. 반대 방향 호출(Repository가 Service를 부르는 등) 금지. (프로젝트가 커지면 S1 헥사고날로 확장)
2. **엔티티를 API 응답으로 직접 내보내지 않는다** — Request/Response DTO를 따로 만든다. 엔티티를 그대로 반환하면 내부 필드(비밀번호 해시 등)가 새고, 연관관계 순환 참조로 직렬화가 터지며, DB 컬럼을 바꾸는 순간 API가 깨진다(모바일에선 **이미 설치된 앱이 전부 깨진다**). DTO는 컨트롤러 안에 인라인으로 정의하지 않고 별도 파일로.
3. **`@Transactional`은 Service에만** — 컨트롤러·리포지토리에 두지 않는다. 조회 전용 메서드는 `@Transactional(readOnly = true)`.
4. **파일당 클래스 하나** — 찾기 쉽고 충돌이 적다. (S1의 Command/Query `In`/`Out` inner class만 예외)
5. **새 엔티티는 무조건 공통 `BaseEntity` 상속** — `id`·`created_at`·`updated_at`·`deleted_at`(소프트 삭제) 제공. `created_at`을 손으로 재선언하지 않는다(십중팔구 `deleted_at`을 빠뜨림). **"삭제"를 `is_active=false`로 표현하지 않는다** — 의미가 다르다(유령 데이터 사고의 원인). **소프트 삭제는 코드로 강제한다** — 각 엔티티에 `@SQLDelete(sql = "UPDATE <테이블> SET deleted_at = now() WHERE id = ?")`와 `@SQLRestriction("deleted_at IS NULL")`(Hibernate)를 붙인다. 그래야 `repository.delete()`가 행을 지우지 않고, `findById`·파생 쿼리도 삭제된 행을 돌려주지 않는다. "조회할 때마다 조건을 기억해서 붙이기"에 맡기지 않는다.
6. **엔티티를 바꾸면 같은 커밋에 Flyway 마이그레이션** — `ddl-auto=validate`라 누락 시 앱이 뜨지 않는다. DDL은 멱등(`IF NOT EXISTS`).
7. **인가는 `@PreAuthorize`로만** — 필터에 URL 경로 하드코딩 금지(경로 규칙이 전원 403을 낸 사고 사례). ⚠ 보안 설정 클래스에 **`@EnableMethodSecurity`가 없으면 `@PreAuthorize`는 에러 없이 무시**되어 누구나 접근할 수 있다. 프로젝트를 만들 때 한 번 추가하고, §8 Layer 5의 "권한 없음 403" 테스트로 실제로 막히는지 확인한다. 필터 체인은 **기본 거부**로 둔다: `anyRequest().authenticated()` — 로그인·토큰 갱신·Swagger·헬스체크처럼 로그인 없이 열어야 하는 경로만 `permitAll`로 나열한다(이것은 "경로 하드코딩"이 아니라 공개 목록이다). `anyRequest().permitAll()`은 금지.
8. **HTTP 메서드** — 생성 `POST` / 수정 **`PATCH`**(`PUT` 금지) / 삭제 `DELETE` / 조회 `GET`.
9. **외부 연동은 `client/` 패키지로 격리** — 파일 저장소·이메일·결제·소셜 로그인 검증·외부 API마다 클래스 하나씩. 외부 API가 바뀌어도 그 클래스만 고치면 되고, 테스트에서 목으로 바꾸기 쉽다. (S1을 켜면 `client-*` 모듈로)
10. **목록 API는 처음부터 페이지네이션** — 모바일은 화면이 작고 네트워크가 느리다. 전체 목록을 한 번에 내려주지 않고 `page`/`size`(또는 커서)를 받는다. 무한 스크롤(§5-7)과 짝을 이룬다.

## 5. 모바일 앱 필수 규칙

1. **색상·간격·글자 크기 단일 소스** — 모든 값은 `src/theme/`의 토큰(`colors`·`spacing`·`typography`)에서만. 컴포넌트에 `#fff`·`fontSize: 13` 같은 값을 직접 쓰지 않는다. 라이트/다크는 `useColorScheme()`으로 토큰 세트만 바꾼다.
2. **공통 컴포넌트로만 UI 제작** — `Screen`·`AppText`·`Button`·`TextField`·`ListItem` 등. 화면에서 RN 기본 `<Text>`/`<Pressable>`/`<TextInput>`을 새로 스타일링하지 않는다. 공통 컴포넌트 안에서 접근성 속성·글자 크기 대응·Safe Area를 한 번에 보장한다(§5.2).
3. **API는 도메인 클라이언트로만** — 컴포넌트에서 `axios`/`fetch` 직접 호출 금지. `src/api/<domain>.ts` → TanStack Query 훅(`src/queries/<domain>.ts`) 경유. 토큰 첨부·갱신은 인터셉터가 전담(§3.1-2·3).
4. **서버 상태 ≠ 클라이언트 상태** — 서버 데이터는 TanStack Query 캐시에, Zustand엔 UI 상태만. 둘을 복제하지 않는다.
5. **외부 입력은 경계에서 Zod로 검증** — 폼 입력과 API 응답 파싱 지점.
6. **모든 화면은 4가지 상태를 처리한다: 로딩 · 에러 · 빈 목록 · 오프라인** — 지하철·엘리베이터에서도 앱은 쓰인다. TanStack Query의 `onlineManager`를 NetInfo와, `focusManager`를 `AppState`와 연결하고(앱이 다시 앞으로 오면 데이터를 새로 받는다), 요청 실패 시 "다시 시도" 버튼을 보여준다. 흰 화면이나 무한 로딩으로 두지 않는다.
7. **긴 목록은 `FlashList`(또는 `FlatList`)로** — `ScrollView` 안에서 `map`으로 그리지 않는다(항목이 많아지면 메모리 폭증·버벅임). 목록은 서버 페이지네이션(§4-10)과 무한 스크롤로.
8. **네이티브 패키지는 `npx expo install`로만 설치** — `npm install`로 최신을 넣으면 SDK와 버전이 어긋나 빌드가 깨진다. 설치 후 `npx expo-doctor`로 호환성을 확인한다. 네이티브 코드가 포함된 패키지를 추가했다면 개발 빌드를 다시 만든다(`npx expo run:ios|android`).
9. **플랫폼 분기는 공통 컴포넌트 안에만** — `Platform.OS === 'ios'` 분기를 화면 곳곳에 흩뿌리지 않는다. 기능은 iOS·Android **둘 다에서** 확인한다(§8 Layer 6).
10. **기기 권한은 쓰는 순간에 요청하고, 거부를 처리한다** — 앱 시작하자마자 카메라·위치·알림 권한을 한꺼번에 묻지 않는다. 거부하면 기능을 대신할 방법이나 "설정에서 켜기" 안내를 보여준다. 권한 설명 문구는 `app.config`(Expo config plugin)에 반드시 넣는다 — **iOS는 설명 문구 없이 권한을 요청하면 앱이 즉시 종료된다.**
11. **로컬 API 주소는 기기마다 다르다** — `EXPO_PUBLIC_API_URL`로 주입하고 코드에 박지 않는다.
    | 실행 환경 | 백엔드 주소 |
    |---|---|
    | iOS 시뮬레이터 | `http://localhost:8080` |
    | Android 에뮬레이터 | `http://10.0.2.2:8080` (또는 `adb reverse tcp:8080 tcp:8080` 후 `localhost`) |
    | 실기기(개발 빌드) | `http://<내 PC의 LAN IP>:8080` — PC와 같은 Wi-Fi, PC 방화벽에서 8080 허용 |

    HTTP(비암호화)는 개발 중에만 쓴다. 출시 빌드는 HTTPS만 허용된다(S10).

12. **한 개념을 두 곳에 등록하는 구조는 문서화** — 예: 탭 화면(`src/app/(tabs)/`)과 탭 아이콘·라벨 설정(`(tabs)/_layout.tsx`). 한쪽만 고치는 사고가 나면 규칙으로 추가.
13. **개발 빌드를 기본으로, Expo Go는 화면 확인용** — 소셜 로그인·푸시·Skia 같은 네이티브 기능은 Expo Go에서 동작하지 않거나 다르게 동작한다. `expo-dev-client`를 설치하고 `npx expo run:ios|android`로 만든 **개발 빌드**에서 확인한다. Expo Go는 UI만 빠르게 볼 때 쓴다.
14. **`ios/`·`android/` 폴더는 직접 고치지 않는다** — `expo run`·`prebuild`가 `app.config`로부터 **생성하는 폴더**라 다시 생성하면 직접 고친 내용이 사라진다. 네이티브 설정은 `app.config`와 config plugin으로만 바꾸고, 두 폴더는 `.gitignore`에 넣는다.

### 5.2 접근성·기기 대응

> 목표 기준: **WCAG 2.2 AA + iOS/Android 플랫폼 접근성 기준.** 접근성은 장애가 있는 사용자만을 위한 것이 아니다. 노안이 와서 글자를 키워 둔 부모님, 한 손으로 지하철 손잡이를 잡은 사람, 햇빛 아래 화면을 보는 사람 모두를 위한 것이다. 사용자층이 중장년·고령층이면 이 절이 가장 중요한 규칙이 된다.

**접근성**

1. **누를 수 있는 모든 요소에 역할과 이름** — `accessibilityRole`(`button`·`link`·`checkbox` 등)과 `accessibilityLabel`. 특히 **아이콘만 있는 버튼**은 라벨이 없으면 스크린리더가 "버튼"이라고만 읽는다. 선택·비활성 상태는 `accessibilityState`로.
2. **이미지** — 내용을 전달하는 이미지는 `accessibilityLabel`로 설명, 장식용은 `accessible={false}`로 스크린리더에서 제외.
3. **입력칸에 보이는 라벨** — placeholder는 라벨을 대신하지 못한다(입력하면 사라진다). 에러 메시지는 입력칸 가까이 텍스트로 보여주고, 제출 실패 시 `AccessibilityInfo.announceForAccessibility`로 읽어 준다.
4. **색만으로 정보를 전달하지 않는다** — 오류를 빨간색으로만 표시하지 말고 아이콘·문구를 함께.
5. **명도 대비** — 본문 글자 4.5:1, 큰 글자·아이콘 3:1 이상. `src/theme/` 색 토큰을 정할 때 라이트·다크 모두 한 번 검사하면 전 화면에 적용된다(§5-1).
6. **시스템 글자 크기를 따른다** — `allowFontScaling={false}`로 끄지 않는다. 기기 설정에서 글자를 **가장 크게** 해도 글자가 잘리거나 버튼이 겹치지 않아야 한다(고정 높이 대신 패딩, 한 줄 고정 대신 줄바꿈 허용). 탭 라벨처럼 공간이 정말 부족한 곳만 `maxFontSizeMultiplier`로 상한을 둔다.
7. **터치 영역 iOS 44×44pt · Android 48×48dp 이상** — 작은 아이콘은 `hitSlop`이나 패딩으로 영역을 키운다.
8. **제스처만으로 되는 기능 금지** — 스와이프 삭제·길게 누르기 메뉴에는 같은 일을 하는 버튼을 함께 둔다(스크린리더·운동 장애 사용자는 제스처가 어렵다).
9. **스크린리더 읽기 순서가 화면 순서와 같아야 한다** — 카드처럼 한 덩어리인 요소는 `accessible`로 묶어 한 번에 읽히게 한다.
10. **움직임 줄이기 설정 존중** — 기기의 "동작 줄이기"가 켜져 있으면 애니메이션을 끄거나 줄인다(Reanimated `useReducedMotion()`).

**기기 대응** 11. **작은 화면부터** — 폭 360dp(작은 Android)·375pt(iPhone SE)에서 가로로 잘리지 않아야 한다. 고정 `width` 대신 `flex`·퍼센트·`maxWidth`. 12. **Safe Area** — 노치·다이내믹 아일랜드·홈 인디케이터에 내용이 가리지 않게 `react-native-safe-area-context`를 쓴다(RN 기본 `SafeAreaView`는 쓰지 않는다 — Android에서 동작하지 않는다). 공통 `Screen` 컴포넌트에서 한 번에 처리. 13. **키보드가 입력칸을 가리지 않게** — 입력 화면은 `KeyboardAvoidingView`(폼이 많으면 react-native-keyboard-controller)로 감싸고, 스크롤로 입력칸이 보이게 한다. 두 플랫폼 모두 확인. 14. **다크 모드** — 시스템 설정을 따르고, 토큰(§5-1)만 바꿔서 지원한다. 다크에서도 대비(§5.2-5)를 만족해야 한다. 15. **화면 방향을 정한다** — 세로 고정이면 `app.config`의 `orientation: "portrait"`로 명시. 가로를 지원하면 가로에서도 잘림 없이 확인.

## 7. 명령어

> ⚠ 스캐폴딩 후 **실제로 실행해 확인한 명령만** 남긴다.
> 선행 조건:
>
> - 백엔드: **Docker 실행 중**이어야 한다(`bootRun`의 docker compose, Testcontainers 통합 테스트 모두 필요). Docker 없이 통합 테스트가 실패하면 코드 문제로 오판하지 말 것.
> - 앱: **iOS 시뮬레이터는 macOS + Xcode에서만** 돌아간다. Windows·Linux는 Android Studio 에뮬레이터 또는 실기기(개발 빌드)를 쓴다. Android 빌드는 React Native 환경 설정 문서가 권장하는 JDK를 `JAVA_HOME`으로 둔다(백엔드는 `jvmToolchain(25)`로 JDK 25를 따로 쓰므로 둘 다 설치).
> - E2E: Maestro CLI 설치(`curl -fsSL "https://get.maestro.mobile.dev" | bash`), Java 17 이상.

```bash
# 백엔드 (단일 모듈 기준 — S1 멀티모듈 명령은 §9 S1 참고)
./gradlew build                          # 전체 빌드 + 테스트
./gradlew build -x test                  # 테스트 제외
./gradlew test                           # 테스트만
./gradlew test --tests "MemberServiceTest"   # 단일 테스트
./gradlew bootRun                        # 실행 (docker compose로 DB 자동 기동)

# 모바일 앱
npm install
npx expo start                           # 개발 서버 (개발 빌드가 설치된 시뮬레이터/에뮬레이터/실기기가 접속)
npx expo run:ios                         # 개발 빌드 생성·설치 (처음 1회 + 네이티브 패키지·app.config를 바꿨을 때)
npx expo run:android
npx expo install <패키지>                 # SDK 호환 버전으로 설치 (§5-8)
npx expo-doctor                          # 의존성·설정 호환성 점검 (인터넷 연결 필요)
npx tsc --noEmit                         # 타입 검사
npm run lint                             # expo lint
npm test                                 # jest (1회 실행 후 종료)
npm test -- src/lib/date.test.ts         # 단일 테스트 파일
maestro test .maestro/                   # E2E (시뮬레이터/에뮬레이터에 앱이 설치·실행 중이어야 함)
```

> `package.json`: 스크립트는 `"test": "jest"`, `"lint": "expo lint"`. Expo 문서 예제의 `"test": "jest --watchAll"`은 watch 모드라 끝나지 않으므로 검증 게이트에서 멈춘다 — 쓰지 않는다.
> Jest 최소 설정(이게 없으면 첫 `npm test`부터 실패한다):
>
> ```jsonc
> // package.json
> "jest": {
>   "preset": "jest-expo",
>   "setupFiles": ["./node_modules/@react-native-community/netinfo/jest/netinfo-mock.js"]
> }
> ```
>
> 네이티브 모듈(Secure Store·권한 등)은 테스트에서 `jest.mock('expo-secure-store')`처럼 목으로 바꾼다. 목 없이 import하면 "native module is null" 에러가 난다.
> TypeScript는 `npx expo install`이 아니라 `npm install -D typescript@6.0.3`으로 고정한다(§2.2).

## 8. 하네스 6계층 — AI 작업 방식

**Layer 1 — 계층형 규칙 로딩 (항상 로드, 짧게)**

```
~/.claude/CLAUDE.md               # 개인 전역: git·언어·문서 스타일
CLAUDE.md                         # 루트: §3 전역 규칙 + 켠 선택 규칙 목록
{{BACKEND_DIR}}/CLAUDE.md         # §4 백엔드 필수 규칙 (+ 켠 백엔드 선택 규칙)
{{MOBILE_DIR}}/CLAUDE.md          # §5 앱 필수 규칙 (+ 켠 앱 선택 규칙)
```

**Layer 2 — 온디맨드 상세 규칙 (필요할 때만 읽음)**
`.claude/rules/*.md` — 기본: `architecture` · `conventions` · `migration` · `testing` · `build-test` · `navigation`(라우트 구조) · `native-modules`(패키지 추가 절차). (S1을 켜면 `module-structure` · `domain-modules`, S10을 켜면 `release` 추가)
자동 로드되지 않으므로 컨텍스트(토큰)를 아낀다.
규모가 커지면 Layer 5의 "변경 유형별 테스트" 표와 테스트 작성 규칙은 `rules/testing.md`로 옮기고, 루트엔 TDD 사이클과 검증 게이트만 남긴다.
각 CLAUDE.md에 **"어떤 작업이면 어떤 파일을 먼저 읽어라"** 를 명시한다. 예: "네이티브 패키지를 추가하기 전 `rules/native-modules.md`를 읽는다."

**Layer 3 — 런북 스킬**
`.claude/skills/<name>/SKILL.md` — 반복되는 절차를 단계별 문서로 둔다. 예:

- `new-feature` — 기능 추가 순서: 마이그레이션·엔티티 → 서비스 → API → 앱 API 클라이언트·쿼리 훅 → 화면. 단계마다 Layer 5의 테스트 먼저.
- `db-migration` — 마이그레이션 작성·검증 절차.
- `add-native-module` — `npx expo install` → `app.config` 플러그인·권한 문구 → 개발 빌드 재생성 → 두 플랫폼 확인.

"기능 추가해줘"를 받으면 런북을 순서대로 실행한다. 사람의 체크리스트를 코드화한 것. (스토어 출시 런북은 S10)

**Layer 4 — 브랜치 + PR 게이트**

- `main`에 직접 커밋 금지. 항상 **기능 브랜치 → PR → 리뷰 → 머지**.
- (선택) 여러 작업을 동시에 할 때는 워크트리로 격리: `git worktree add .worktrees/<branch> -b <branch> --no-track origin/main`
- **커밋·푸시는 사람이 직접 실행한다.** AI는 `git commit`/`git push`를 실행하지 않고, 검증이 끝나면 다음만 조언한다.
  - **커밋 단위:** 어떤 파일을 어떤 커밋에 묶을지, 커밋 순서(예: `.gitignore` 정리 → 기능 변경).
  - **커밋 내용:** 커밋별 메시지 제안(저장소의 기존 메시지 스타일에 맞춤) + 섞이면 안 되는 파일 경고(로컬 덤프·시크릿·빌드 산출물·`ios/`·`android/` 생성 폴더·`.env`).
- DB 데이터 삭제, 외부 서비스로의 전송처럼 되돌리기 어렵거나 밖으로 나가는 작업은 **실행 전 사용자 확인**.

**Layer 5 — TDD 개발 루프 (모든 코드 변경에 적용)**

기능 추가·버그 수정·리팩터 모두 아래 사이클로 진행한다. 한 사이클 = 한 가지 행위.

1. **RED** — 요구사항을 실패하는 테스트로 먼저 쓴다. 실행해서 **의도한 이유로 실패하는지** 확인한다(컴파일 에러·오타·설정 문제로 실패하면 RED가 아니다).
2. **GREEN** — 그 테스트를 통과시키는 **최소한의** 구현만 한다. 테스트를 고쳐서 통과시키지 않는다.
3. **REFACTOR** — 통과 상태를 유지하며 정리한다. 정리할 때마다 테스트를 다시 돌린다.
4. 다음 행위로 1부터 반복.

**테스트 작성 규칙**

- 테스트 이름은 행위를 문장으로: `"잔액이 부족하면 출금을 거절한다"`.
- 목(mock)은 **경계에만**(Repository·`client/`·외부 API·기기 기능 모듈). 엔티티·도메인 객체는 목으로 만들지 않는다.
- **테스트를 약하게 해서 통과시키기 금지** — 테스트 삭제, `skip`/`only`, 단언 완화, 기대값 끼워맞추기, 스냅샷을 이유 없이 갱신(`-u`)하기. 기존 테스트의 기대값은 요구사항이 바뀐 경우에만 바꾸고, 바꾼 이유를 보고한다.
- 플래키 테스트는 재시도로 덮지 않고 원인(시간·순서·공유 상태·애니메이션 대기)을 고친다.
- 위치: 백엔드 `src/test/kotlin/`에 같은 패키지 구조로, 단위 `*Test.kt` · 통합 `*IntegrationTest.kt`. 앱은 대상 파일 옆 `*.test.ts(x)`, E2E는 `.maestro/*.yaml`.

**단계별 검증 게이트** — 앞 게이트를 통과해야 다음으로 간다.

| 시점           | 실행                                                                                                             | 통과 기준                                |
| -------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 사이클마다     | 방금 쓴 테스트 1개                                                                                               | RED(의도한 실패) → GREEN 확인            |
| 작업 단위 완료 | `./gradlew test` / `npm test`                                                                                    | 전부 통과                                |
| 커밋 조언 전   | `./gradlew build` · `npx tsc --noEmit && npm run lint && npm test && npx expo-doctor`(expo-doctor는 인터넷 필요) | 전체 통과, 새 경고 없음                  |
| PR 전          | 위 + `maestro test .maestro/` (가능한 플랫폼 모두)                                                               | 전부 통과                                |
| PR 전 마무리   | Layer 6                                                                                                          | 시뮬레이터/에뮬레이터에서 실제 동작 확인 |

완료를 보고할 때는 **실행한 명령과 결과(통과/실패 수)** 를 함께 적는다. 실패나 건너뛴 단계(예: "macOS가 아니라 iOS는 확인 못 함")는 숨기지 않고 그대로 보고한다.

**Layer 6 — 검증 문화**
"완료"라고 말하기 전에 실제로 돌려 확인한다. Layer 5 게이트를 통과한 뒤, 로컬에서 백엔드(`./gradlew bootRun`)와 앱(`npx expo start`)을 띄워 한다.

- 백엔드: `local` 프로필의 개발용 로그인(§3.1-4)으로 받은 토큰으로 API를 직접 호출해 응답 확인(Swagger UI 또는 curl).
- 앱: 개발용 계정으로 로그인(§3.1-4)해 바꾼 화면을 직접 눌러 본다. 아래 체크리스트를 한 번씩:
  - [ ] **iOS와 Android 둘 다** (한쪽만 가능하면 못 한 쪽을 보고에 적는다)
  - [ ] **작은 화면**(360dp / iPhone SE급)
  - [ ] 기기 설정에서 **글자 크기 최대**
  - [ ] **다크 모드**
  - [ ] **스크린리더**(iOS VoiceOver / Android TalkBack)로 주요 버튼이 이름대로 읽히는지
  - [ ] **네트워크를 끊고** 오프라인 상태 표시와 복귀 후 재시도 (Android 에뮬레이터·실기기는 비행기 모드. iOS 시뮬레이터엔 비행기 모드가 없으므로 Mac의 Wi-Fi를 끄거나 Network Link Conditioner 사용)
  - [ ] 입력 화면에서 **키보드가 입력칸을 가리지 않는지**
  - [ ] 권한을 **거부**했을 때의 동작
- 테스트 통과만으로 끝내지 않는다. `skip`/`only`/TODO 스텁은 완료 증거가 아니라 블로커다.

# Part B. 선택 규칙 — 조건에 해당할 때만 켠다

## 9. 선택 규칙

> 켜는 방법: §1 체크리스트에 표시하고, 해당 규칙을 백엔드/앱 CLAUDE.md로 옮긴다. 켜지 않은 규칙은 지운다.
> 처음 개발하는 팀은 **전부 끈 상태로 시작**하는 것을 권한다. 대부분은 "규모가 커져서 아팠던 경험"에서 나온 규칙이라, 작은 프로젝트에선 비용만 든다.

### S1. 헥사고날 아키텍처 + CQRS + 멀티모듈 (백엔드)

**켜는 조건:** 도메인(기능 묶음)이 5개 이상 / 개발자 3명 이상 / 1년 이상 운영 예정 — 둘 이상 해당하면 고려.
**왜:** DB·웹 프레임워크·외부 API가 바뀌어도 비즈니스 로직이 그대로 남게 하고, 모듈 경계로 팀원 간 충돌을 줄인다. 대신 기능 하나에 파일이 7~8개 필요하다.

1. **의존 방향 고정** — `adapter → application → domain`. Domain은 Spring/JPA/외부 SDK 의존 금지. ArchUnit 테스트로 강제. (§4-1의 3계층을 대체)
2. **CQRS** — Command(상태 변경)와 Query(조회)를 인바운드 포트 인터페이스부터 분리. 각각 `In`/`Out` inner data class(§4-4의 유일한 예외).
3. **외부 연동은 `client-*` 모듈로** — `client-storage`, `client-email` … (§4-9를 모듈 단위로 확장)
4. **Flyway는 전용 `migration` 모듈**에 둔다.
5. 두 단어 패키지명은 언더스코어(`app_api`).

```
{{BACKEND_DIR}}/
├── app-api/            # bootJar — REST API 서버
├── app-worker/         # bootJar — 스케줄러·백그라운드 워커
├── common/  auth/  auth-api/  rbac/  migration/  mvc-wrapper/  client-*/   # 인프라·공통
└── {domain}/src/main/kotlin/{{BASE_PACKAGE}}/{domain}/
    ├── domain/                     # *DomainEntity · vo · exception · event
    ├── application/
    │   ├── service/                # *Service (유스케이스, @Transactional)
    │   ├── port/inbound/           # *Command · *Query
    │   └── port/outbound/          # *OutboundPort
    └── adapter/
        ├── presentation/web/       # Controller + request/response DTO (파일 분리)
        └── infrastructure/jpa/     # *JpaEntity · *RepositoryAdapter
```

```kotlin
interface CreateMemberCommand {
    fun create(command: In): Out

    data class In(val name: String, val email: String)
    data class Out(val id: Long)
}
```

**추가 테스트:** 유스케이스는 outbound port만 목으로 대체한 서비스 테스트 / 헥사고날 경계는 ArchUnit(모듈 추가 시 대상에 포함, `./gradlew build`에 포함되어 실행).
**추가 명령:**

```bash
./gradlew :app-api:build                          # 특정 모듈만
./gradlew :{domain}:test                          # 모듈 테스트
./gradlew :{domain}:test --tests "XxxServiceTest" # 단일 테스트
./gradlew :app-api:bootRun                        # 실행
```

### S2. DB 외래키(FK) 제약 금지

**켜는 조건:** 서비스를 여러 개로 나누거나 DB를 서비스별로 분리할 계획이 있을 때 / 대용량 테이블 마이그레이션을 무중단으로 해야 할 때.
**끈 상태(기본):** FK로 데이터 무결성을 DB가 지켜 준다. 처음 배우는 팀은 FK를 쓰는 편이 안전하다.

1. 관계는 ID 컬럼 + 인덱스로만. `@ManyToOne`/`@JoinColumn`으로 실제 FK를 만들지 않는다.
2. FK가 해 주던 무결성 검사(존재하지 않는 ID 참조, 부모 삭제 시 자식 처리)는 Service에서 직접 하고 테스트로 보장한다.

### S3. Redis (분산락 · 작업 큐)

**켜는 조건:** 서버를 2대 이상 띄울 때 / 같은 작업이 동시에 두 번 실행되면 안 될 때(분산락) / 오래 걸리는 작업을 백그라운드로 넘길 때(Stream 큐 — 이미지 변환, 대량 푸시 발송 등).
(모바일 API는 무상태 토큰 인증(§3.1-4)이라 세션 공유용 Redis는 필요 없다.)

1. 백그라운드 작업은 `app-worker`(또는 별도 스케줄러)가 Redis Stream을 소비한다.
2. **Redis Stream은 소비자와의 공유 계약** — 스트림 키·태스크 타입·필드를 생산자·소비자 양쪽 동시에 바꾼다. 한쪽만 바꾸지 않는다.

**추가 테스트:** 스트림 키·태스크 타입·필드 계약 테스트(소비자 쪽과 같은 픽스처 공유) — Testcontainers(Redis).

### S4. AI 처리 전용 Python 서비스

**켜는 조건:** 검색·임베딩·RAG·음성인식(STT) 같은 AI/지식 처리가 있을 때.

1. AI 처리는 `{{AI_SERVICE}}`(Python)가 직접 한다. Kotlin에서 재구현하지 않는다. 백엔드는 프록시(예: `/api/v1/kb/**`)로 위임만. **앱이 AI 서비스·외부 AI API를 직접 부르지 않는다**(키 노출, §3.1-11).
2. 응답이 몇 초 이상 걸리는 AI 작업(문서 임베딩·음성 변환 등)은 요청 안에서 기다리지 않고 작업 큐로 넘긴다 → **S3을 함께 켠다.** 앱은 진행 상태를 조회하거나 완료 푸시(S9)를 받는다.
3. 예외(예: Kotlin에서 LLM API를 직접 호출)를 둘 땐 이 문서에 "의도된 예외"로 명시한다. 명시되지 않은 예외는 드리프트로 간주.

### S5. Vault 시크릿 관리

**켜는 조건:** 운영 서버가 여러 대 / 여러 사람이 운영 시크릿을 다룸 / 보안 감사 대응이 필요할 때. (S10 전제)
**끈 상태(기본):** §3-1대로 로컬 `.env`, 배포 환경은 S10의 플랫폼 시크릿.

1. 모든 백엔드 시크릿은 Vault에서 `${ENV}`로 주입, 부팅 시 로드, 변경 시 롤아웃.
2. 기능을 지우면 Vault 키까지 지운다.

### S6. API 네임스페이스 분리

**켜는 조건:** 관리자 전용 API나 서버끼리만 부르는 내부 API가 생겼을 때.

1. 내부용 / 외부 노출용 / 관리 데이터용 경로를 나눈다. (예: `/api/v1/**`, `/internal/**`, `/admin/**`)
2. 관리자용 컨트롤러는 클래스에 `@PreAuthorize("hasRole('ADMIN')")`를 붙여 통째로 막는다(§4-7 방식 유지). (배포 후엔 게이트웨이에서도 내부용 경로 차단 — S10)

### S7. 오프라인 편집·동기화 (ST/DR 버퍼 · bulk sync)

**켜는 조건:** 네트워크가 없어도 입력·편집이 되어야 할 때(기록·체크리스트·현장 입력 앱) / 여러 항목을 한꺼번에 편집하고 저장하는 화면이 있을 때.

1. **ST/DR 이중 버퍼** — 서버에 저장된 값(ST)과 편집 초안(DR) 분리. 계산·표시 지표는 **항상 ST**, 편집은 DR에, 저장 성공 시에만 DR→ST.
2. **초안은 기기에 보존** — 앱이 백그라운드로 가거나 종료돼도 DR이 사라지지 않게 로컬에 저장한다(개인정보·토큰은 §3.1-2 규칙대로 제외). 로그아웃 시 삭제(§3.1-18).
3. **연결되면 변경분만 한 번에** — 백엔드는 `PATCH /<resource>/sync` 하나(`findAllByIds` + `saveAll` 단일 트랜잭션, 삭제는 sync에 싣지 않는다). 앱은 행마다 호출하지 않는다(N+1 금지).
4. **충돌 규칙을 정한다** — 다른 기기에서 먼저 바뀐 항목은 `updated_at`을 비교해 거절하고, 사용자에게 어느 값을 남길지 보여준다. "나중에 저장한 쪽이 조용히 덮어쓰기"로 두지 않는다.

**추가 테스트:** `PATCH /sync` — 변경분만 저장 + 중간 실패 시 전체 롤백 + 충돌 시 거절(Testcontainers) / 앱 스토어 — 표시는 ST 기준인지, 저장 전 DR이 ST를 바꾸지 않는지, 오프라인 → 온라인 복귀 시 sync 1회 호출(Jest).

### S8. 차트

**켜는 조건:** 통계·추이 그래프가 있을 때.

1. victory-native + react-native-skia 사용(§2.3). Skia는 네이티브 모듈이라 `npx expo install` 후 개발 빌드가 필요하다(Expo Go 불가).
2. 차트 색은 `src/theme/` 토큰에서만(§5-1), 다크 모드 포함.
3. **차트만으로 정보를 전달하지 않는다** — 스크린리더 사용자를 위해 핵심 수치를 텍스트 요약(`accessibilityLabel` 또는 표)으로 함께 제공한다.

### S9. 푸시 알림

**켜는 조건:** 앱이 꺼져 있을 때도 사용자에게 알려야 할 때(리마인더·채팅·상태 변경).

1. **권한은 가치가 보이는 순간에 요청** — 첫 실행에 바로 묻지 않고, "알림을 받으면 무엇이 좋은지" 보여준 뒤 요청한다. 거부해도 앱은 동작한다(§5-10).
2. **기기 토큰은 서버가 사용자별로 관리** — 로그인 시 등록, 로그아웃·탈퇴 시 삭제, 발송 실패로 무효 판정된 토큰은 정리한다. 한 사용자가 여러 기기를 가질 수 있다.
3. **알림 내용에 민감정보를 넣지 않는다** — 잠금 화면에 그대로 보인다. "새 메시지가 있습니다" 수준으로 쓰고 상세는 앱 안에서.
4. **알림을 누르면 해당 화면으로** — 알림 데이터에 Expo Router 경로를 담고, 받은 값은 딥링크처럼 검증한다(§3.1-10).
5. 푸시 수신은 개발 빌드 + **실기기**에서 확인한다(시뮬레이터·에뮬레이터는 제약이 있다). 발송 서버 키(FCM·APNs)는 백엔드 시크릿으로만 관리한다.

**추가 테스트:** 토큰 등록·삭제·무효 토큰 정리(Kotest + Testcontainers) / 알림 탭 시 올바른 화면으로 이동(Jest + RNTL).

### S10. 스토어 출시·운영

**켜는 조건:** 로컬을 넘어 실제 사용자에게 앱을 배포할 때(TestFlight·내부 테스트 트랙 포함).
**끈 상태(기본):** 로컬 개발과 시뮬레이터/에뮬레이터 검증(§8 Layer 6)까지만 다룬다.

**백엔드 배포**

1. API는 **HTTPS로만** 공개한다. iOS(ATS)와 Android 출시 빌드는 기본적으로 HTTP 요청을 막는다.
2. 배포 환경의 시크릿은 배포 플랫폼의 시크릿 기능으로 주입한다(규모가 커지면 S5 Vault). `ddl-auto=validate`는 운영에서도 유지한다.
3. 요청 횟수 제한(§3.1-14)은 배포 플랫폼·리버스 프록시 기능으로 보강할 수 있다. 내부용 경로(S6)는 게이트웨이에서도 차단.

**앱 출시** 4. **EAS Build / Submit**으로 스토어용 빌드를 만들고 제출한다. 빌드용 환경 변수는 EAS 환경 변수로 관리한다(`EXPO_PUBLIC_`은 여전히 공개값, §3.1-11). 5. **옛 버전 앱과의 호환(가장 중요)** — 스토어에 나간 앱은 사용자가 업데이트할 때까지 계속 돌아간다. API 응답 필드를 **삭제·이름 변경하지 않고 추가만** 한다. 깨야 하면 `/api/v2`를 새로 열고(§3-4) 옛 버전은 일정 기간 유지한다. 필요하면 "최소 지원 앱 버전" API로 강제 업데이트 안내를 띄운다. 6. **EAS Update(OTA)는 JS 변경에만** — 네이티브 패키지·권한·`app.config` 변경은 스토어 재출시가 필요하다. 네이티브 변경이 섞인 업데이트를 OTA로 내보내지 않는다(runtimeVersion 관리). 7. **스토어 심사 요구사항 확인** — 개인정보 처리방침 URL, 앱 내 계정 삭제 기능(계정 생성이 있으면 필수), 권한 사용 설명, 소셜 로그인을 제공하면 Apple 로그인 등 동등한 로그인 옵션 요구 여부, Google Play 데이터 보안 양식. 출시 전 각 스토어의 최신 가이드라인을 확인한다. 8. **크래시·에러 수집** — 출시 후엔 사용자의 기기에서 난 오류를 볼 방법이 없다. 크래시 리포팅 도구를 연결하되, 개인정보를 싣지 않는다(§3.1-16).

**배포 흐름 (§8 Layer 4에 추가)** 9. 스테이징이 있으면 `feature → staging` 검증(내부 테스트 트랙·TestFlight) 후 `staging → main`(운영 배포·스토어 제출) 승격을 **사람이 승인**. 10. 배포·스토어 제출·운영 DB 변경은 **실행 전 사용자 확인**. AI가 운영 환경에 직접 배포하거나, 스토어에 제출하거나, 운영 DB를 수정하지 않는다. 11. 배포 후 검증: 스토어 테스트 빌드를 실기기에 설치해 §8 Layer 6 체크리스트를 한 번 더 한다.

**하네스 추가**

- `.claude/rules/release.md` — 버전 번호 규칙(앱 버전·빌드 번호), 환경별 API 주소, 롤백 방법.
- `.claude/skills/` — `release`(스토어 출시) · `hotfix`(긴급 수정 — OTA 가능 여부 판단 포함). 운영 규모가 커지면 `db-account-admin`(DB 계정 관리) · `ops-access`(운영 접속, 예: Teleport).

## 11. 규칙을 추가하는 방법

버그·사고가 한 번 나면 그 교훈을 규칙으로 남긴다 — 문서가 곧 팀의 기억이다.

```markdown
N. **<한 줄 규칙 — 금지/강제 형태로>** — <왜>. (<어떤 사고에서 나왔는지 1줄>)
```

- 모든 작업에서 지켜야 하는 것 → 해당 CLAUDE.md 필수 규칙에.
- 특정 조건에서만 필요한 것 → 선택 규칙(켜는 조건과 함께)이나 `.claude/rules/<topic>.md`에.
- 순서가 있는 절차 → `.claude/skills/<name>/SKILL.md`에.
- 기계로 강제할 수 있으면(ArchUnit·ESLint 규칙·`expo-doctor`) 문서보다 **도구로 강제**를 우선한다.
